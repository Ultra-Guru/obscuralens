v5.1 turns ObscuraLens from "a tool you install" into "a program you
download": the headline feature is the **desktop beta program** -- a
single-file executable per platform, built and published by GitHub Actions
on every `v*-beta*` tag, wrapping the full 14-kind investigation engine,
the analyst toolbox and the local web UI behind one launcher with
single-instance locking, port probing, branding and update checks.
Around that core, v5.1 ships an **internationalization runtime with 14
languages**, an **offline data catalog of ten new ISO/IANA/MITRE reference
packs**, a first-class **Python SDK** (sync + async) for the REST API, an
**explainable YAML rule engine** with 15 packs and 23 operators, three
**Jinja2 report templates**, and eight new pipeline examples. Roughly
37,700 lines of new code and tests land in this release, all of it
offline-testable, stdlib-first, and Python 3.9 compatible.

This is a **beta**. The binaries are unsigned, the desktop feature set may
still move, and feedback is wanted early -- see [Feedback](#feedback).
For the previous release, see [v5.md](v5.md); for the download and
first-run guide, see [desktop-beta.md](desktop-beta.md).

## Desktop Beta program

The desktop edition packages everything ObscuraLens does into **one
portable executable per platform**: no Python installation, no `pip`, no
virtualenv, no admin rights. Download the file, run it, and a browser
window opens the same single-page web UI that `obscuralens serve` gives
you, served from a loopback-only web server inside the exe. The same
binary is also the complete command-line client.

### What shipped: the `obscuralens.desktop` package

A new import-light package (`obscuralens/desktop/`, seven modules,
stdlib-only at import time) implements the desktop runtime:

| Module | Responsibility |
|---|---|
| `launcher.py` | The launch sequence (below) and `LaunchOptions`; also the `obscuralens-desktop` entry point. |
| `singleinstance.py` | `InstanceLock` -- a `desktop.lock` file in the config directory; a second launch prints the running instance's URL and exits 0 instead of fighting over the port, the SQLite database and the cache. |
| `branding.py` | Pure-ASCII startup banner, beta badge, staged splash lines and About text -- pure ASCII so it renders on Windows `cmd.exe` with a legacy code page. |
| `channel.py` | The release-channel registry: `stable` (regular tags), `beta` (`v*-beta*` pre-releases), `nightly` (rolling tag); asset naming `ObscuraLens-<version>-<platform><ext>`. |
| `updater.py` | GitHub-Releases update checker with sane pre-release version ordering; **never auto-downloads**. |
| `diagnostics.py` | `--diagnostics` environment report: Python, platform, frozen-build status, config paths, optional-dependency availability, offline data-pack stats, optional network probe. |
| `__init__.py` | Re-exports the public surface (`launch`, `LaunchOptions`, `InstanceLock`, diagnostics helpers, channel and updater tools). |

The launch sequence in `launcher.py`:

1. print the desktop banner;
2. acquire the single-instance lock -- a second copy prints the URL of the
   running instance and exits 0;
3. probe for a free TCP port in the configured range (default 8000-8020,
   each candidate tested with a real `bind(2)`);
4. lazily build the FastAPI app and a uvicorn server on a background
   thread (with a clear message when the `web` extra is missing);
5. poll the readiness endpoint (default timeout 15 s);
6. open the system browser (unless `--no-browser`) once the server is
   actually ready, not before;
7. block until `Ctrl+C`, then shut the server down gracefully and release
   the lock.

The update checker compares the running version against the newest GitHub
release of its channel using pre-release-aware ordering: `5.1.0-beta.1`
sorts **below** `5.1.0`, `beta.10` sorts **above** `beta.9`, `rc.1` sorts
above `beta.9` (label rank: nightly < dev/alpha < beta < rc), and bare
`nightly` tags sort below every numbered version. When a newer release
exists the launcher prints a notice with the download URL -- and that is
all it does; the desktop edition never downloads or applies an update by
itself, because silently replacing a running binary is exactly the kind of
behaviour an OSINT tool should not have.

### The desktop CLI commands

```text
obscuralens desktop                  # launch the desktop beta UI
obscuralens desktop --port 8123      # preferred port; free ports probed upward
obscuralens desktop --no-browser     # start the server without opening a browser
obscuralens desktop --diagnostics    # print a desktop diagnostics report and exit
obscuralens desktop --check-update   # check GitHub Releases for a newer beta and exit
obscuralens update check             # the same check, standalone (--channel beta)
```

### The `obscuralens-desktop` console script

`pip install "obscuralens[desktop]"` installs a second entry point,
`obscuralens-desktop`, which runs `obscuralens.desktop.launcher:main`
directly -- the same launcher without going through the general CLI. The
frozen executable uses the same code path, so the exe and the console
script behave identically.

## Release automation

Desktop builds are produced by two new GitHub Actions workflows; neither
requires a maintainer to build anything locally.

### `desktop-beta.yml` (tagged betas)

Triggered by pushing a tag matching `v*-beta*` (or by manual
`workflow_dispatch`, which takes the tag to publish under). It runs a
three-way matrix:

| Platform | Runner | Artifact | Smoke test |
|---|---|---|---|
| `win-x64` | `windows-latest` | `ObscuraLens-<version>-win-x64.exe` | `dist/obscuralens.exe --version` |
| `linux-x64` | `ubuntu-latest` | `ObscuraLens-<version>-linux-x64` | `dist/obscuralens --version` |
| `macos-arm64` | `macos-latest` | `ObscuraLens-<version>-macos-arm64` | `dist/obscuralens --version` |

Each matrix job builds with the PyInstaller spec, smoke-tests the binary
**on its own platform**, stages the versioned asset plus a per-asset
`.sha256` digest, and uploads it as a workflow artifact. A final release
job downloads all three, concatenates the digests into `checksums.sha256`,
and publishes a GitHub **pre-release** whose body carries the full
download instructions (asset table, verify command per platform, first-run
notes). If any platform's build or smoke test fails, no release is
published.

### `desktop-nightly.yml` (rolling nightly)

Runs every day at **03:00 UTC** (plus manual dispatch) and rebuilds the
Windows exe from the default branch tip, refreshing -- not appending to --
a single rolling pre-release under the `nightly` tag. Assets are named
`ObscuraLens-nightly-<YYYYMMDD>-<commit7>-win-x64.exe`, so testers can see
at a glance which commit they are running. The nightly channel is for
testing only; prefer tagged betas for anything serious.

### How a maintainer cuts a beta

```bash
git tag v5.1.0-beta.2
git push origin v5.1.0-beta.2
```

That is the whole procedure. The tag push triggers `desktop-beta.yml`,
which builds, smoke-tests and publishes the pre-release with checksums and
instructions; the `obscuralens update check` command starts reporting the
new version to every running desktop install on its next check.

### The PyInstaller spec fix

A genuine bug is fixed along the way: `scripts/obscuralens.spec`
previously did not collect package data, so a frozen exe shipped **without
the offline data packs** (and would have shipped without the new rule
packs and templates). The spec now bundles all of
`obscuralens/data/*.txt`, `obscuralens/rules/packs/*.yaml` and
`obscuralens/reporting/templates/*.j2` -- which is why
`obscuralens data stats` works inside the exe. The CI `exe` job
(windows-latest, on every push and pull request) builds the executable and
smoke-tests `dist/obscuralens.exe --version`, so a packaging regression
surfaces in CI long before anyone tags a beta.

## Internationalization (14 languages)

ObscuraLens now speaks fourteen languages. The new `obscuralens.i18n`
package ships translations as plain Python modules (one `STRINGS` dict
per locale under `obscuralens/i18n/locales/`, 220 keys each) -- because
the catalogues are code rather than data files they work unchanged inside
the frozen desktop executable, with no gettext binaries, no file I/O and
no third-party dependencies.

| Code | English name | Native name | Direction |
|---|---|---|---|
| `en` | English | English | ltr |
| `zh` | Chinese (Simplified) | 简体中文 | ltr |
| `ja` | Japanese | 日本語 | ltr |
| `ko` | Korean | 한국어 | ltr |
| `de` | German | Deutsch | ltr |
| `fr` | French | Français | ltr |
| `es` | Spanish | Español | ltr |
| `pt` | Portuguese (Brazil) | Português (Brasil) | ltr |
| `ru` | Russian | Русский | ltr |
| `it` | Italian | Italiano | ltr |
| `nl` | Dutch | Nederlands | ltr |
| `pl` | Polish | Polski | ltr |
| `ar` | Arabic | العربية | **rtl** |
| `hi` | Hindi | हिन्दी | ltr |

Every locale carries the identical 220-key catalogue with the same
`{placeholder}` tokens, enforced by the test suite; Arabic is the only
right-to-left language and `is_rtl()` exists so UIs can mirror correctly.

The runtime API:

```python
from obscuralens.i18n import set_language, t, tp, best_match

set_language("de")
t("app.version", version="5.1.0")   # translated, {placeholder} interpolation
tp("plural.results", 5)             # plural-aware: key.zero / key.one / key.many

best_match("zh-CN,zh;q=0.9,en;q=0.8")   # -> "zh" (Accept-Language negotiation)
```

The lookup chain for `t()` is **current language -> English -> the
caller-supplied default -> the key itself**, so a missing translation
degrades to readable text instead of an exception; `tp()` follows the same
chain and falls back to the bare key when no plural form exists.
`best_match()` parses real `Accept-Language` headers: entries are ranked
by quality value, regional subtags resolve to their primary language
(`pt-BR` -> `pt`), `*` matches the default, and unparseable input falls
back to `en`.

From the CLI:

```text
obscuralens i18n list                    # the 14 supported languages
obscuralens i18n list --completion       # ...with key coverage per locale
obscuralens i18n show app.title --all    # one key in every locale
obscuralens i18n match "zh-CN,zh;q=0.9,en;q=0.8"
```

Full guide: [i18n.md](i18n.md).

## Python SDK

`obscuralens.sdk` is a first-class Python client for the ObscuraLens REST
API -- no `requests`, no `httpx`, no SDK toolkit: the transport is built on
`urllib.request` from the standard library, so the SDK adds **zero new
dependencies** and works wherever ObscuraLens does.

```python
from obscuralens.sdk import ObscuraLensClient, AsyncObscuraLensClient

with ObscuraLensClient("http://127.0.0.1:8000", api_key="...") as client:
    result = client.lookup("domain", "example.com")
    report = client.risk("domain", "example.com")
    print(report.band, report.score, report.explain())

async with AsyncObscuraLensClient("http://127.0.0.1:8000") as client:
    first, second = await client.gather(
        client.lookup("ip", "203.0.113.9"),
        client.lookup("domain", "example.net"),
    )
```

What is inside:

- **`ObscuraLensClient`** -- 66 public methods (64 request methods once
  `close()` and the `transport` property are set aside) covering every
  route the server actually exposes: `lookup` plus one convenience per
  target kind (`ip()`, `phone()`, `username()`, `email()`, `domain()`,
  `url()`, `crypto()`, `hash_()`, `cve()`, `asn()`, `mac()`, `iban()`,
  `imei()`, `coords()`), the investigation endpoints (`investigate`,
  `risk`, `timeline`, `correlate`, `correlate_pair`, `intel`), cases and
  watchlist management, keys and settings, history, exports and reports,
  the seven toolbox tools (including multipart exif/stego uploads built
  with stdlib), batch, and `raw_get` / `raw_post` escape hatches for
  future endpoints.
- **`AsyncObscuraLensClient`** -- 31 of those request methods plus a
  `gather()` helper, wrapped with `asyncio` over a private thread pool,
  Python 3.9-safe.
- **Retry and backoff** -- transport errors, timeouts and HTTP 429 are
  retried with exponential backoff (`backoff * 2**attempt`, capped at
  `max_backoff`); a server `Retry-After` header is honoured over the
  backoff schedule; 4xx/5xx errors are raised immediately.
- **Typed exceptions** -- `SdkError` base (`.message`, `.status`,
  `.payload`) with `TransportError`, `TimeoutError`, `ApiError`,
  `BadRequestError`, `NotFoundError`, `RateLimitError` (carries
  `.retry_after`), `ServerError` and `MalformedResponseError`
  (`.body_text`).
- **Tolerant models** -- 31 dataclasses built via `from_dict` that never
  raise on extra or missing keys and always keep the raw payload; risk
  models carry band helpers and `explain()`.
- **`StaticTransport`** -- a scripted-response test double that records
  every call, ships in the package itself, and is how the SDK's own test
  suite runs fully offline.

The client mirrors the real server behaviour, not the docs' ideal of it:
where `docs/api.md` and `web/app.py` disagreed (case item payloads,
`patterns` parameters), the SDK follows the server. Full method table,
error semantics and more examples: [sdk.md](sdk.md).

## Explainable risk rule packs

`obscuralens.rules` adds a transparent scoring layer that complements the
existing heuristics: instead of a number with no justification, every rule
that fires carries an id, a title, a plain-language reason and a
reference. Rules are authored in a small YAML DSL and evaluated by
`rules/engine.py`:

```yaml
- id: DOMAIN-001
  title: Very young domain
  description: >-
    The domain was registered within the last 30 days. Newly registered
    domains are heavily over-represented in phishing and malware
    distribution...
  severity: medium
  weight: 20
  tags: [age, phishing]
  references: ["MITRE ATT&CK T1583.001"]
  conditions:
    - field: registration.age_days
      operator: lte
      value: 30
```

- **23 operators**: `eq`, `neq`, `in`, `not_in`, `contains`,
  `not_contains`, `startswith`, `endswith`, `regex`, `gt`, `gte`, `lt`,
  `lte`, `exists`, `not_exists`, `empty`, `not_empty`, `is_true`,
  `is_false`, `in_cidr`, `known_pack`, `age_lt_days`, `age_gt_days` --
  including dotted-path field resolution and the `known_pack` operator
  that tests values against the offline data packs.
- **15 packs ship**: one `shared` pack that every kind evaluates, plus one
  pack per target kind:

| Pack | Rules | Pack | Rules |
|---|---|---|---|
| `shared` | 11 | `phone` | 10 |
| `domain` | 16 | `username` | 10 |
| `ip` | 16 | `crypto` | 10 |
| `url` | 12 | `hash` | 10 |
| `email` | 12 | `asn` | 10 |
| `cve` | 11 | `iban` | 10 |
| `mac` | 8 | `coords` | 10 |
| `imei` | 9 | | |

165 rules in total, with unique ids (`DOMAIN-001` style), severities in
`info/low/medium/high/critical`, weights 0-100 and a per-rule explanation.

- **Scores and bands**: matched weights accumulate to a 0-100 score
  (capped), mapped to bands `< 10 clean`, `10-29 watch`, `30-59
  elevated`, `60-79 high`, `>= 80 critical`. Every evaluation returns the
  matched rule ids, per-rule hits and a one-line human summary.
- **Tolerant loading**: corrupt YAML, unknown operators and missing data
  packs degrade to skipped rules and recorded warnings, never exceptions;
  user-supplied pack directories can override the shipped ones via
  `OBSCURALENS_RULES_DIR`.

Full DSL reference, operator semantics and authoring guide:
[rules.md](rules.md).

## Report templates

Three Jinja2 templates under `obscuralens/reporting/templates/` plus a
small renderer (`reporting/template_render.py`) turn stored lookups into
shareable artefacts:

| Template | Output |
|---|---|
| `standalone_report.html.j2` | Single-file HTML report: inline CSS, table of contents, meta grid, per-section tables, risk band strip and score, top signals, footer with version/channel. Opens anywhere, no web server needed. |
| `report.md.j2` | Markdown report: title, meta bullets, contents list, pipe tables, blockquote notes -- for case notes, tickets and PRs. |
| `summary.html.j2` | Executive summary card: risk band and score, top signals, source-health table, disclaimer. |

The renderer registers four filters -- `esc` (HTML-escape), `nl2br`
(newlines to `<br>`), `fmt_pct` (`0.123` -> `12.3%`) and `fmt_date` (ISO
UTC) -- and exposes `render_template(name, **context)` plus the
`render_standalone_html_report` / `render_markdown_report` conveniences.
A missing template raises a friendly error that lists the available
names; `available_templates()` reports what actually shipped. All three
templates are exercised by 86 offline tests, including escaping and
empty-state behaviour.

Every lookup command accepts `--template <name>`, which renders the
result through a shipped template instead of the built-in formatter:

```powershell
obscuralens ip 8.8.8.8 --template standalone_report --risk -o report.html
obscuralens domain example.com --template summary --risk -o summary.html
obscuralens ip 1.1.1.1 --template report.md -o report.md
```

A bare `--template` lists the available names; abbreviated names such as
`standalone_report` or `summary` resolve to the shipped file. With
`--risk`, the risk verdict feeds the templates' band strip (`band`),
`score` and `top_signals`.

## Pipelines

Eight new examples join the three that shipped with v5.0
(`domain-review`, `ip-triage`, `brand-abuse`), each a commented,
runnable YAML under `pipelines/examples/`:

| Example | What it does |
|---|---|
| `email-triage.yaml` | Triage a suspicious email address and its mail domain; breach exposure drives the escalation gate; exports Markdown + JSON. |
| `phishing-url-review.yaml` | End-to-end review of a suspected phishing URL **and** its host domain: redirect chain, page verdicts, WHOIS age, mail posture, two escalation gates. |
| `brand-username-audit.yaml` | Audit a brand handle across every platform the username tracker covers; flags broad footprints for impersonation review. |
| `crypto-screening.yaml` | Screen a crypto address for attribution flags (mixer, cluster tags) and attach the activity-profile score; reconstructs the event timeline. |
| `cve-patch-priority.yaml` | Score one CVE for patch scheduling across three evidence levels: KEV listing, EPSS probability, CVSS severity. |
| `malware-hash-response.yaml` | First-response enrichment for a suspicious file hash across scanners and YARA sources; family attribution gates the incident track. |
| `network-sweep.yaml` | Sweep an IP and pivot to its announcing AS and an observed hostname, covering address, routing and name service in one run. |
| `weekly-exec-brief.yaml` | Aggregate the week's investigations into one executive brief via the correlation engine -- run it after the daily pipelines. |

Run them by path or by name, exactly like the v5.0 examples:

```text
obscuralens pipeline run email-triage --set target=suspicious@example.com
obscuralens pipeline run weekly-exec-brief
```

## Engineering notes

- **Version and channel.** `obscuralens.__version__` is `5.1.0` and a new
  `obscuralens.__desktop_channel__` constant is `"beta"`, consumed by the
  branding, channel registry and update checker so a frozen exe knows
  what it is without filesystem sniffing.
- **pyproject.toml additions.** A `desktop` extra (`fastapi>=0.110`,
  `uvicorn>=0.29`); a second console script
  `obscuralens-desktop = "obscuralens.desktop.launcher:main"`; and
  `[tool.setuptools.package-data]` entries for `data/*.txt`,
  `rules/packs/*.yaml` and `reporting/templates/*.j2` so wheel installs
  actually contain the packs, rules and templates.
- **CI.** Beyond the existing lint/test/sanity/web/tui/docker jobs, CI
  gained an `exe` job (windows-latest) that builds the PyInstaller
  executable on every push and pull request, smoke-tests
  `dist/obscuralens.exe --version` and uploads the artifact -- exe
  regressions surface long before a beta tag. The `package` job builds
  the sdist/wheel and validates it with `twine check`.
- **No new required dependencies.** Everything new is standard library
  plus PyYAML and Jinja2, which were already core dependencies in 5.0.
  The i18n catalogues, the data catalog, the SDK transport, the desktop
  package and the rule engine core import nothing third-party at all;
  matplotlib, numpy and friends remain confined to the extras that always
  had them.
- **Python 3.9+ unchanged.** No `match` statements, no PEP 604 unions, no
  3.10+ stdlib in any new module; `typing.Optional/List/Dict` throughout,
  verified by the ruff configuration (`target-version = "py39"`).
- **Four new CLI subcommands** are wired into `obscuralens/commands.py`:
  `desktop`, `update`, `i18n` and `data`. They are additive; no existing
  command changed shape.
- **Tests are offline.** The six new test files mock every network
  interaction (the SDK suite runs against `StaticTransport`), so the whole
  v5.1 test additions run on an air-gapped machine.

## Compatibility & upgrade

- **Nothing breaking from 5.0.** No public API was removed or renamed; the
  14 tracker kinds, the CLI commands, the REST routes and the stored
  SQLite history all work exactly as before. A 5.0 database opens
  unchanged in 5.1.
- **Configuration format unchanged.** Same file, same keys, same defaults;
  `obscuralens config` output is identical apart from the version string.
- **New commands are additive.** `obscuralens desktop`, `update`, `i18n`
  and `data` are new subcommands; no existing subcommand changed its
  arguments.
- **New packages are import-light.** `import obscuralens` does not pull in
  any of the new modules; each is imported where it is used, so startup
  time and dependency surface for existing users are unchanged.
- **Same Python floor.** 3.9+, as in 5.0; none of the new code requires
  3.10+ syntax or stdlib.
- **Upgrading**: `pip install --upgrade obscuralens` (or download the new
  exe for the desktop edition). Downgrading back to 5.0 is also safe --
  5.1 writes no new persistent state beyond its own lock file.
